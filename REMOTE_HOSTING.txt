REMOTE HOSTING: GITHUB + RENDER

Every station and projector opens the same HTTPS address. Devices need Internet
access to that address; they do not need to reach each other on campus Wi-Fi.
GitHub stores the code. Render runs the Python server and stores the database.
GitHub Pages alone cannot run this Python backend or shared SQLite database.

This package prepares deployment; no live service or paid account was created.

SETUP
1. Create a GitHub repository (private is fine). Upload the CONTENTS of this
   folder into its root: render.yaml, server.py, trailmix.html, and the other
   supplied code/docs. Do not upload real database files, data/, or secrets.
2. Sign in to https://dashboard.render.com and choose New > Blueprint.
   Connect your GitHub repository and use render.yaml at the repository root.
3. Review the paid web service and 1 GB disk charges shown before deploying.
   This config uses plan 0.5c-512mb (formerly Starter). Free web services do not
   support the persistent disk required by this app. See current pricing:
   https://render.com/pricing
4. Enter a long, private TRAILMIX_ACCESS_CODE and a separate
   TRAILMIX_SAFETY_PIN when Render prompts. Share only the team code with
   operators; keep the Safety PIN with Safety personnel. Store these values in
   Render's environment settings, never in the repository.
5. Deploy. Open the HTTPS URL Render provides, enter the team code, then your
   name. Use that same URL on every station and projector.
6. Connect each browser once. In Devices, give it a useful name and assign its
   person and station. Browser profiles have separate identities; tabs in the
   same profile share one. This does not scan the campus network.
7. Practice with two devices: record a label/fill operation, confirm the other
   device updates, export logs, restart the service, reconnect, and confirm
   records remain. Test campus access before the production session.

STORAGE AND UPDATES
The persistent disk is mounted at /var/data. TRAILMIX_DB points to
/var/data/trailmix.sqlite3. Keep a SINGLE service instance: SQLite and the live
update notifications run together on that instance. Disk data persists across
normal deploys/restarts; deleting the disk deletes its records.

Automatic application deploys are disabled so a code push does not restart the
line unexpectedly. Push code updates to GitHub and manually deploy from Render
between production sessions. Browsers must sign in again after a restart.
Changing environment variables or the Blueprint can also restart the service.

Export records regularly. Render disk snapshots provide a recovery option;
keep separate downloaded exports. For a complete SQLite backup, use a maintenance
window with writes stopped and copy the database and associated files, or use
SQLite's backup API to produce a consistent backup before downloading it. Never
commit operational databases to GitHub. JSON exports are for analysis, not an
implemented restore/import interface. This package does not upload existing
local production records automatically; an initial cloud deployment starts fresh.

NETWORK AND LIVE UPDATES
One authenticated server-sent events (SSE) connection delivers changes after
sign-in, with a keepalive about every 20 seconds. This is one open request, not
new requests every two seconds. No live connection or recurring API requests run
while the access-code screen is waiting. Explicit saves and view/name changes
still send requests. If a proxy interrupts the live connection, the browser
reconnects; Reconnect is also available. Keep Internet access during production.
Partly entered weights and open dialogs are protected from background updates.

OTHER HOSTS
Any Python host with HTTPS, long-lived HTTP responses and a persistent writable
disk can run python -u server.py. It must provide PORT, TRAILMIX_DB,
TRAILMIX_ACCESS_CODE, TRAILMIX_SAFETY_PIN and TRAILMIX_HTTPS=1. The Dockerfile is
also supplied for hosts with Docker volumes. A static-only host is insufficient.
